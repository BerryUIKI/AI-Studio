## Summary

[package-windows-release.ps1:96](https://github.com/BerryUIKI/AI-Studio/blob/c1c5dbeaace01fc5e3fa68d8e3ebf410583b775b/scripts/package-windows-release.ps1#L96) copies a development venv's executable, site-packages, and original `pyvenv.cfg`; it does not provision the complete base Python distribution that the venv references. It still emits a package when the venv is absent. The script builds the Tauri binary before building the frontend, creating missing/stale-asset risk. Engine installation requires Git without establishing a bundled/provisioned prerequisite.

## Reproduction or validation

Review package-windows-release.ps1: it stages a development venv/config, allows missing Python staging with a warning, and builds the native binary before frontend assets. An isolated copy of the venv executable/config executed successfully only with sys.base_prefix outside that copy, confirming base-runtime dependence. This is not a clean-VM launch failure; a clean Windows VM still needs testing. Git provisioning for engine setup must also be established.

## User impact

Source-machine checks can pass while a recipient cannot start Berry or install engines. An additional isolated probe copied the venv executable and configuration and confirmed that its `sys.base_prefix` still points outside the copied runtime. Packaging probe result. This demonstrates base-runtime dependence; a clean VM failure is not claimed because that test was not run.

## Proposed approach

Package a pinned redistributable runtime, build frontend before embedding it, fail incomplete builds, and run launch/onboarding/inference/exit on a Windows VM with no Python, Git, or development tools.
