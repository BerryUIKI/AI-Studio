## Summary

The creative POST waits for execution before returning its task ID. The frontend cannot use that ID to cancel while waiting. [creative_runner.py:147](https://github.com/BerryUIKI/AI-Studio/blob/c1c5dbeaace01fc5e3fa68d8e3ebf410583b775b/backend/app/runners/creative_runner.py#L147) signals an event but checks it after awaited execution; it can return `cancelled` while a cloud job continues. Comfy interrupt is not scoped to an individual queued task.

## Reproduction or validation

Trace creative submission and cancel_task. The POST returns its task ID after execution finishes, while cancellation is checked after awaited execution. Cloud work can continue after a local cancelled response; Comfy interrupt is not scoped to a queued task. Validate with a blocking fake runner and a provider that does not support remote cancellation.

## User impact

A user cannot reliably stop a long operation, and task state can overstate cancellation.

## Proposed approach

Return an ID at submission, stream state independently, distinguish cancel-requested from confirmed cancellation, disclose unsupported remote cancellation, and add bounded concurrency/queue ownership.

## Acceptance criteria

- [ ] Return an identifiable task immediately and stream status independently.
- [ ] The UI can request cancellation while creation is running.
- [ ] Distinguish cancel-requested from confirmed cancellation and disclose remote limitations.
- [ ] Use bounded queue/concurrency and task-specific ownership where engine APIs allow it.
