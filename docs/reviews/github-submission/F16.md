## Summary

[useCanvasStore.ts:430](https://github.com/BerryUIKI/AI-Studio/blob/c1c5dbeaace01fc5e3fa68d8e3ebf410583b775b/frontend/src/stores/useCanvasStore.ts#L430) sends the full run payload on every new connection. The backend has no durable run-id deduplication, and the frontend does not consistently reject events from obsolete runs. Heartbeats are sent even though the server does not continue reading them after the initial request.

## Reproduction or validation

Inspect useCanvasStore.runWorkflow: every WebSocket onopen sends the full run payload. The server accepts a submission again rather than resuming a durable run, and UI events are not isolated by run ID. Client PINGs are also sent after the server stops receiving messages. Duplicate paid execution was not attempted; validate with a controllable connection and a counted fake runner.

## User impact

A transport failure can initiate duplicate inference or charges; a late event can overwrite a newer run's state. This was not reproduced with a paid service.

## Proposed approach

Separate submission from subscription, persist an idempotency key, resume an existing run, check run identity on every event, and implement or remove the heartbeat contract.

## Acceptance criteria

- [ ] Separate idempotent submission from subscription/resume.
- [ ] Reconnect to an existing durable run without a second inference call.
- [ ] Ignore stale events from previous runs.
- [ ] Implement a matched heartbeat protocol or remove the unsupported heartbeat.
- [ ] Disconnect/reconnect tests assert execution count and final state.
