## Summary

App and multiple canvas components subscribe to entire Zustand stores, so timer/progress changes can rerender unrelated UI. [ViewContainer.tsx:19](https://github.com/BerryUIKI/AI-Studio/blob/c1c5dbeaace01fc5e3fa68d8e3ebf410583b775b/frontend/src/components/navigation/ViewContainer.tsx#L19) mounts every view and merely hides inactive ones, retaining effects/listeners. Independent status polling and full node snapshots add overhead. The production bundle contains a 645.91 kB JavaScript chunk.

## Reproduction or validation

App and canvas components subscribe to whole stores; progress changes can notify unrelated views. ViewContainer mounts all views and hides inactive ones while effects/listeners continue. Independent polling and full node history snapshots add work. The reviewed production build's JS chunk was 645.91 kB (184.78 kB gzip); no startup/frame-time benchmark was run.

## User impact

Idle work and update costs grow with the canvas, even when another view is open.

## Proposed approach

Use selectors, suspend inactive effects, lazy-load secondary views, share polling, and profile a realistic large canvas before choosing additional optimizations. Bundle size alone is not a measured startup failure.
